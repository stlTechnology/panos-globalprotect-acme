GlobalProtect certificate auto-renewal

A public SSL certificate for the GlobalProtect portal and gateway that renews itself and installs itself on the Palo Alto, from a small scheduled task on an on-site Windows machine.

PAN-OS 11.2 · standalone Windows Server 2019+ / Win 10+ PowerShell 7 (5.1 fallback) Cert: Let's Encrypt · GoDaddy SSL · other ACME CA DNS: GoDaddy · Cloudflare
90 → 45 days

Let's Encrypt cert lifetime (shrinking by 2028). Renews automatically when a third of the lifetime is left.

Daily

The task checks once a day. It touches the firewall only when there's a new cert.

0 clicks

After go-live, no manual renewals. You get an event-log alert if anything fails.

~1 hour

Rough time for prerequisites, staging test and go-live, plus a short maintenance window.

Why now

The maximum life of public SSL certificates is shrinking: 200 days since March 2026, 100 days from March 2027, 47 days from March 2029. Renewing a VPN certificate by hand every few weeks isn't sustainable.

Status

Field-tested (2026-10, PAN-OS 11.2 standalone, Windows Server 2022, PowerShell 7.6): Let's Encrypt production cert with Cloudflare DNS, deployed to GlobalProtect and confirmed working with the Windows GP client and on iOS.

Not yet field-tested: a real renewal replacing an existing cert (T2b), the failure-revert call (T2c), GoDaddy DNS, GoDaddy SSL (ACME/EAB), other ACME CAs, and Windows PowerShell 5.1 on a real server.

Open issue: least-privilege firewall role. Only Superuser works; custom roles, cryptoadmin and Device administrator all fail the import (see Before you start).

01How it works

Every day at 03:17 the Windows task runs these steps:

CheckIs the cert due for renewal? Usually no, so the run ends here.
Prove the domainAdds a temporary _acme-challenge TXT record through the GoDaddy or Cloudflare DNS API.
Get the certFrom Let's Encrypt, your GoDaddy SSL purchase, or another ACME CA.
InstallImports the cert and key into the Palo and commits only its own change.
VerifyConnects to the portal and confirms it's serving the new cert, then logs the result.

Pick your combination

Where the certificate comes from and where your DNS is hosted are separate choices. Setup asks for both.

"Certificate from Cloudflare": not possible yet

Cloudflare's normal certificates only live on its proxy, and its Origin CA certificates are only trusted by that proxy. GP clients would reject them, and GlobalProtect can't run behind the Cloudflare proxy anyway.

Cloudflare announced a public certificate authority on 29 Sept 2026 but isn't issuing yet. When it does, choose "Cloudflare or another ACME CA" and paste its directory URL. No script changes needed.

Fails safe

If a push fails, the script undoes its uncommitted firewall changes, logs an error, and tries again the next day. The old cert keeps working until the new one is verified.

02Before you start

Tick these off before running setup. The checkboxes are just for you; nothing is saved.

Windows machine (on site)

DNS hosted at Cloudflare

DNS hosted at GoDaddy

Which one am I? What matters is who hosts DNS (the nameservers), not where the domain was bought. Setup detects it for you. DNS somewhere else? Move the zone, or CNAME _acme-challenge.vpn to a zone at Cloudflare/GoDaddy.

Never paste API keys or tokens into email, chat or tickets. Setup asks for them on the server and stores them locked down.

Certificate from GoDaddy (paid SSL only)

GoDaddy ACME certificates are domain-validated (DV), the same level as Let's Encrypt.

Palo Alto firewall

The API key is tied to the acme-api password. If the password changes or expires, renewals stop until you create a new key (see Operations).

03Install

Copy the folder (the two .ps1 files plus this guide) to the Windows machine. Open PowerShell as Administrator in that folder:

pwsh -ExecutionPolicy Bypass -File .\Install-PaloAcme.ps1

No PowerShell 7? Use powershell instead of pwsh. The daily task runs with whichever one you start setup with.

There are no switches to remember. Setup asks questions, checks your answers, and installs nothing until you confirm.

You never create the Let's Encrypt certificate (or an account) by hand. This setup script creates both. It registers a Let's Encrypt account using your email, proves you own the name with a temporary TXT record, receives the cert, and pushes it to the firewall. After that, the daily task renews it the same way.
  1. "Get the certificate from Let's Encrypt (free, auto-renewing - recommended)?"

    Press Enter for yes. If you answer n, you get these choices:

    • 1) GoDaddy paid SSL certificate. Setup fetches the ACME details using a GoDaddy key and your customer number. If that fails, it asks you to copy them from GoDaddy → SSL → Manage All → ACME Automation → ACME Setup.
    • 2) Cloudflare or another ACME CA. Paste the CA's ACME directory URL. Setup asks later whether it needs EAB keys.
    • 3) Let's Encrypt STAGING. A test run. The cert isn't trusted by clients, and safe test defaults are filled in.
    • 4) Back to the first question.
  2. Names on the cert

    GP portal FQDN first, then any extra names, separated by commas, e.g. vpn.contoso.com, gw.contoso.com.

  3. "DNS for contoso.com is hosted at Cloudflare … Use the Cloudflare API to prove domain control?"

    Setup looks up your public nameservers and suggests the provider. If you answer no, or it's not detected, you get: 1) Cloudflare  2) GoDaddy  3) Cancel. Picking a provider your nameservers don't point to is refused, since the CA wouldn't see the record.

  4. Contact email

    The certificate authority sends expiry and policy notices here.

  5. Firewall management IP or FQDN

    Setup connects to it right away. If it can't, it stops and tells you what to check. If this machine doesn't trust the firewall's management certificate (the factory default one), it asks before continuing without checking it (default no).

  6. Certificate object name on the firewall

    Use a new name (default gp-acme; acme-test for staging). Don't reuse your current cert's name. You'll point GlobalProtect at the new name once, at go-live.

  7. Where to confirm the portal serves the new cert

    Defaults to the portal FQDN. Enter the portal's public IP if the name doesn't resolve from inside, or none to skip.

  8. Summary → "Proceed?"

    Read it. Answer n and nothing on the machine has changed.

  9. DNS credentials: GoDaddy key + secret, or Cloudflare token

    Tested immediately: the GoDaddy key against the API, the Cloudflare token for access to your zone. If it fails, you can try again or stop.

  10. Only for a GoDaddy certificate: ACME details

    Fetched automatically with your customer number. If DNS is at Cloudflare, it first asks whether to use a GoDaddy API key for this. If you answer no, or the lookup fails, type the three values from the ACME Setup page.

  11. The firewall's acme-api login

    Setup uses it once to create an API key. The password itself is not stored.

  12. "Run the first deploy to the firewall now?"

    Yes runs the scheduled task right away (as SYSTEM, the same way it will run every day).

Re-running setup is normal

Run it again to go from staging to production, switch certificate source or DNS provider, or enter a new key or token. Your previous answers come back as defaults. To change the daily time: .\Install-PaloAcme.ps1 -At 04:30.

04Test plan

Do these in order. T0–T3 use a throwaway cert object, so GlobalProtect users aren't affected.

T0

DNS credentials work

Do

Run setup and enter the GoDaddy key or Cloudflare token when asked.

Pass when

No error after entering it. GoDaddy: 401 = wrong or OTE key, 403 = account not allowed. Cloudflare: 401/403 = bad token, "can't see zone" = token not scoped to this domain.

T1

Staging certificate issued

Do

Setup: answer n → 3 (STAGING), accept the defaults (acme-test, check none), confirm your real DNS provider.

Do this even if you'll use a GoDaddy cert. GoDaddy has no staging, so prove DNS and the firewall here first (T3g covers GoDaddy).

Pass when

Setup prints the cert's Subject, NotAfter and Thumbprint. This proves the DNS validation works.

T2a

First import to the firewall

Do

Say yes to "Run the first deploy now", or run Start-ScheduledTask 'PaloAcme Renew'.

Pass when
  • Application log, source PaloAcme: event 1000
  • Firewall → Device → Certificates: acme-test has a key and a staging intermediate
  • Write down its serial number
T2b

Renewal overwrites in place

most important
Do

In admin PowerShell, force a real renewal, then run the task again:

$env:POSHACME_HOME='C:\ProgramData\PaloAcme\posh-acme'
Import-Module Posh-ACME
Submit-Renewal -Force
Start-ScheduledTask 'PaloAcme Renew'
Pass when

acme-test shows a new serial, still with a key, and the commit is OK. This is exactly what happens every renewal.

If it fails, see Troubleshooting.

T2c

Safety-net undo works

Do

Paste in the key from C:\ProgramData\PaloAcme\apikey.txt and your firewall IP:

curl.exe -k -d "type=op" -d "key=PASTE_KEY" --data-urlencode "cmd=<revert><config><partial><admin><member>acme-api</member></admin></partial></config></revert>" https://10.0.0.1/api/
Pass when

The response contains status="success". This proves the undo used after a failed deploy is allowed for this role.

T3

Commit is clean

Do

Open the newest log in C:\ProgramData\PaloAcme\logs, and Monitor → Logs → Configuration on the firewall.

Pass when

The log shows the commit job OK, and the firewall shows the commit by acme-api with only the cert changes.

T3g

GoDaddy certificate (only if using one)

Do

Re-run setup: answer n → 1 (GoDaddy SSL), keep acme-test and check none. Let it deploy.

Pass when

Event 1000, and acme-test on the firewall is now issued by GoDaddy. Only the GoDaddy ACME step is new here.

Account creation fails with an EAB or key error? Re-run and type the Key Data from GoDaddy's ACME Setup page when the automatic lookup is skipped.

T4

Production + go-live

Do

Follow Go live below.

Pass when

Event 1000, a GP client connects without warnings, and the served chain has 2 or more certs.

T5

Alerts reach you

Do

Temporarily put a wrong IP in C:\ProgramData\PaloAcme\config.json ("Firewall"), run the task, then put it back.

Pass when

Event 1001 appears and your RMM / monitoring alerts on it.

05Go live

Switch GlobalProtect to the auto-renewing cert. You only do this once.

Do this in a maintenance window

Changing the GP SSL/TLS profile can briefly drop connected VPN users. A mistake here locks users out until it's reverted.

  1. Re-run setup for production

    Press Enter at the first question (Let's Encrypt), or choose GoDaddy. Object name gp-acme. Check address = portal FQDN or IP.

  2. Let it deploy, and expect one error

    The first run logs 1001 "serves X, expected Y". That's correct: the cert is on the firewall, but GP still uses the old one.

  3. Point GlobalProtect at it (by hand, once)

    Device → Certificate Management → SSL/TLS Service Profile (the one GP uses) → Certificate = gp-acme → OK → Commit.

  4. Run the task again

    Start-ScheduledTask 'PaloAcme Renew' should now log 1000. It retries because the thumbprint is only saved after a successful check.

  5. Check from outside

    Connect with a GP client. Optionally, from any machine with OpenSSL:

    # must print 2 or more (leaf + intermediate)
openssl s_client -connect vpn.contoso.com:443 -servername vpn.contoso.com -showcerts </dev/null 2>/dev/null | grep -c 'BEGIN CERTIFICATE'
# expiry dates and serial number
openssl s_client -connect vpn.contoso.com:443 -servername vpn.contoso.com </dev/null 2>/dev/null | openssl x509 -noout -dates -serial
  6. Clean up

    Delete the acme-test certificate on the firewall and commit. Keep the old commercial cert until it expires, as a fallback.

06Optional: same cert for the admin web UI

Same mechanism, no second install. Add the firewall's management name to the cert and point the management profile at the same object. Every renewal then updates GlobalProtect and the admin UI together.

Do this after GlobalProtect go-live works.

  1. Pick a management name in the same public zone

    e.g. fw.contoso.com. It does not need a public DNS record, since validation only writes a TXT record. Add an internal DNS A record pointing it at the mgmt IP.

  2. Re-run setup with both names

    Keep your other answers. Names = vpn.contoso.com, fw.contoso.com (GP name first). A new cert is issued and pushed into gp-acme.

  3. Create a management profile (firewall, once)

    Device → Certificate Management → SSL/TLS Service Profile → Add mgmt-acme, certificate gp-acme, min version TLSv1.2.

  4. Assign it to the admin UI

    Device → Setup → Management → General Settings (gear) → SSL/TLS Service Profile = mgmt-acme → Commit. The web UI restarts and you'll be logged out. Browse to https://fw.contoso.com: no certificate warning.

  5. Optional bonus

    Re-run setup with firewall address fw.contoso.com. The mgmt cert is now trusted, so setup verifies the firewall connection instead of asking to skip.

Public name exposure

Every name on a public certificate is published in Certificate Transparency logs, so anyone can see fw.contoso.com exists. Use a non-obvious name, or skip this section if that matters for this site.

Locked out of the GUI?

SSH or console into the CLI and run:

configure
delete deviceconfig system ssl-tls-service-profile
commit

The admin UI goes back to its default self-signed certificate.

The daily task rides out the admin web server restarting during a commit. A separate admin certificate (different name or CA) would need a second install and isn't supported by setup.

Key rotation (optional, after T2b passes)

By default the private key is reused across renewals; the certificate itself still changes about every 30 days. That's the field-proven path on PAN-OS. For a new key on every renewal:

$env:POSHACME_HOME='C:\ProgramData\PaloAcme\posh-acme'
Import-Module Posh-ACME
Set-PAOrder -AlwaysNewKey

Then repeat T2b on a test object to confirm the firewall accepts a cert-and-key swap.

08Troubleshooting

SymptomCause → fix
GoDaddy check fails with 401Wrong key or secret, or an OTE (test) key. Create a production key.
GoDaddy check fails with 403The account isn't allowed to use the API. Alternative: CNAME _acme-challenge to a DNS zone at a provider that has an API.
Cloudflare check fails with 401/403Wrong, revoked or expired token. Create a new one (Before you start → Cloudflare).
Cloudflare "can't see zone"The token's Zone Resources doesn't include this domain. Edit the token and add the zone.
Setup says DNS is "not GoDaddy or Cloudflare"The zone is hosted elsewhere. Move it, or CNAME _acme-challenge to a zone at Cloudflare/GoDaddy.
Issuance fails mentioning CAAA CAA record doesn't allow your CA. Add letsencrypt.org (or godaddy.com), or remove the restrictive CAA records.
Served-cert check fails although the GUI shows the new certThe portal record is Proxied (orange cloud) in Cloudflare. Set it to DNS only.
"Cannot reach https://… (curl exit 7/28)"Machine not in the mgmt Permitted IP list, or a routing or firewall-rule issue.
"Couldn't get ACME details from the GoDaddy API"Wrong customer number, or a reseller account. Enter the values from GoDaddy → SSL → Manage All → ACME Automation → ACME Setup.
GoDaddy order fails with "no available product"Your GoDaddy SSL plan has no ACME issuance left (basic DV: 1 credit, 2 refreshes a year). Use the Automated DV SSL plan, or Let's Encrypt.
1001 "Import of … failed. missing subject field"The cert has no subject (Let's Encrypt tlsserver profile). Setup now always asks for classic: re-run setup.
"You do not have an available product" (GoDaddy)No active SSL purchase or credit is linked to those ACME credentials.

Event 1001 403 "Type [import] not authorized for user role"The role's XML API tab doesn't allow Import.

09Security & limits

Security

  • Secrets are stored in C:\ProgramData\PaloAcme, readable only by SYSTEM and Administrators. Any local admin on this machine can read them, so keep it a restricted server.
  • The firewall API key is passed to curl privately, never on the command line, so process auditing doesn't log it.
  • A GoDaddy key can edit all DNS in that account. A Cloudflare token can be limited to one zone and DNS only, which is better. Either way, keep it off general-purpose machines.
  • acme-api currently needs Superuser, so a stolen API key means full control of the firewall from any address allowed to reach the mgmt interface. Restrict Permitted IP to this server.

Where secrets are stored

All under C:\ProgramData\PaloAcme. The folder is readable only by SYSTEM and Administrators (inheritance removed).

SecretFileProtection
Firewall API keyapikey.txtPlain text, folder permissions only
Cloudflare token / GoDaddy keyposh-acme\...\pluginargs.jsonPosh-ACME alt plugin encryption; its key sits in the same folder, so in practice folder permissions
ACME account key, cert private keyposh-acme\...Folder permissions

The acme-api password is never stored; it is only used once to generate the API key. Any unattended renewal job has to be able to read its own credentials, so the real controls are a narrow firewall role, Permitted IP, and limiting who is admin on this machine.

Known limits

  • Standalone firewall only. For an HA pair, target the active unit (config sync copies the cert). Panorama-managed setups aren't covered.
  • GoDaddy ACME issues domain-validated (DV) certs, the same level as Let's Encrypt.
  • DNS automation covers GoDaddy and Cloudflare. Other DNS hosts need CNAME delegation. Posh-ACME supports about 60 providers if one needs adding.
  • Cloudflare's public CA isn't issuing yet (announced Sept 2026). The "other ACME CA" option is ready for it.
  • Windows Server 2016 has no built-in curl.exe.
  • Field-tested on one site so far (see Status at the top). The test plan above is the real validation for yours.
